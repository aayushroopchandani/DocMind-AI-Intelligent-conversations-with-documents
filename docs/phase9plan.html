Before you startFour things that stop this from being simple wiring

01

There is no endpoint that returns an execution result

9.14.1 specifies GET /analysis/runs/{run_id}/execution; it does not exist. A result.preview.json blob is published, but the worker passes plan_summary through on the execution path, so final_dataset_ids and final_artifact_ids are never populated either. Turn on the engine today and an analysis run computes a correct answer that the user cannot see. This is a backend gap sitting inside what looks like a frontend phase, and it gates everything downstream.

02

The existing capture cannot answer the handshake

captureWorkbookContext reads values, formulas, types, formats and merges. WorkbookPatchContext additionally needs per-sheet used_range_a1, protected_ranges, table_ranges and drawing_ranges, plus a protected flag per cell — and a TypeScript computeContextHash that reproduces canonical_context_payload byte for byte, because the server recomputes it and rejects a mismatch. Same file also hardcodes hidden_rows: [] and hidden_columns: [], so the backend's privacy accounting always sees zero hidden rows.

03

Every mutation currently bumps the workbook revision

univer-host.tsx dispatches BUMP_WORKBOOK_REVISION and schedules a debounced save on every Univer MUTATION. A seven-operation patch would advance the revision seven times and save seven times, which breaks the receipt invariant that one patch advances the logical revision exactly once. The coordinator in 9.13.3 is not optional polish.

04

One-undo in Univer 0.25.1 is an open question

The only batching API in the pinned version is IUndoRedoService.__tempBatchingUndoRedo, and it carries an explicit @deprecated — This is a temporary solution. We are going to refactor the undo redo service shortly. It is not on the facade; you reach it through the protected injector. The cleaner route exists — pushUndoRedo({unitID, undoMutations, redoMutations}) is public, and the facade exposes syncExecuteCommand and bulk setValues/setFormulas — but registering one DocMind patch command with correct undo state is a genuine spike. This is the highest-variance item left in the phase.

PracticeHow to get the most out of each session

  • One session, one surface. Sessions are cut so that backend and frontend rarely mix — S8 is the only deliberate crossing, and only because hash parity needs both sides in one head. Crossing that boundary casually is what makes a session run out of room.
  • Open with the baseline, not the goal. Run the suite first (.venv/bin/python -m unittest discover -s tests -t . -q, or npm run typecheck) so a pre-existing failure is never mistaken for something you caused.
  • Hand over the card, not the plan. Paste the session's goal, file list and done-when verbatim. The 1,655-line phase plan is reference material for the specific subsection, not context to load wholesale.
  • Name the files. Every card lists them because the fastest way to lose a session is to spend it rediscovering where things live.
  • End green, end committed. Each session should close with tests passing and the repo shippable — the flags mean an unfinished frontend never breaks the product.
  • Do not flip both flags together. That is the one genuinely bad move available: it parks every edit run at WAITING/proposal on a handshake nothing answers, holding a live rectangle reservation.
